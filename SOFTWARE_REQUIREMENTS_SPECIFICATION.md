## 1. Introduction

### 1.1 Purpose

This document specifies the requirements of the ADK-Powered Travel Planner. It is derived from the Software Design Document (SDD) 1.0.0, with one change: the user interface is a **Next.js** web application instead of Streamlit. Where the two documents differ, this one states the required behavior; the SDD will be updated once the Next.js interface is built.

### 1.2 Scope

The application suggests flights, accommodation, and activities for a trip. It allows users to:

- Enter a trip: origin, destination, dates, budget, and number of travellers
- Receive two or three suggestions each for flights, stays, and activities
- See which parts of a plan failed, while still receiving the parts that succeeded
- See the travel-guide sources used, with their license
- Call the planner from other programs over an HTTP API

The application runs fully self-hosted at no cost, or in the cloud on Vercel. Suggestions are generated by a language model and are illustrative: they are not live availability, live prices, or bookable offers. The application has no user accounts and stores no trip history.

### 1.3 Product perspective

The application is a set of five services: a Next.js web application, a Host agent, and three specialist agents (Flight, Stay, Activities). The Host is the only agent clients call; it calls the specialists in parallel and merges their answers. Each specialist retrieves travel guidance from a Wikivoyage index and asks a language model for structured JSON.

#### 1.3.1 System interfaces

The web application calls the Host's `POST /run` endpoint. The Host calls each specialist's `POST /run`. Specialists call a language-model provider (Ollama or OpenAI) and read a local guidance index. An ingest command builds the index from Wikivoyage.

#### 1.3.2 User interfaces

A single-page web application with a trip form, a progress indicator, three result tables, warnings for failed parts, and a collapsible list of sources. It is usable with a keyboard and a mouse, and on desktop and mobile screen widths.

#### 1.3.3 Hardware interfaces

None. Self-hosting with Ollama needs about 3 GB of disk for models and about 4 GB of free memory; no GPU is required.

#### 1.3.4 Software interfaces

| Interface | Purpose |
| --- | --- |
| Ollama HTTP API (`/api/chat`, embeddings) | Local generation and embeddings |
| OpenAI API (chat completions with strict JSON schema, embeddings) | Cloud generation and embeddings |
| MediaWiki API (`action=query`) | Downloading Wikivoyage articles, at index build time only |
| OTLP over HTTPS | Optional metrics export to Grafana Cloud |

#### 1.3.5 Communications interfaces

All messages are JSON over HTTP. Communication between the browser and the web application, and between the web application and the Host, uses HTTPS in the cloud deployment.

#### 1.3.6 Memory constraints

Each cloud function must fit the hosting platform's bundle limit. The specialist agents, with the guidance index, are about 226 MB uncompressed.

#### 1.3.7 Operations

Operators start the stack, set environment variables, build or rebuild the guidance index when the destination list changes, and read logs and metrics. There are no scheduled jobs.

#### 1.3.8 Site adaptation requirements

All site-specific values (service addresses, model provider, keys, timeouts, index location) are environment variables. No code changes are needed between sites.

#### 1.3.9 Interfaces with services

Optional: Grafana Cloud for metrics. Cloud hosting: Vercel.

### 1.4 Product functions

1. Collect and validate a trip request.
2. Plan the trip with three specialist agents running in parallel.
3. Ground suggestions in retrieved Wikivoyage passages and cite them.
4. Return partial plans when parts fail.
5. Protect the public API with a key.
6. Build and maintain the guidance index.
7. Export operational metrics.

### 1.5 User characteristics

| User | Characteristics |
| --- | --- |
| Traveler | Uses a web browser; no technical knowledge assumed |
| API client | A developer calling the HTTP API with a key |
| Operator | Comfortable with a command line, Docker, environment variables, and Vercel |

### 1.6 Limitations

- Suggestions come from a language model and may be inaccurate.
- Guidance covers only destinations in the index (20 by default), by exact name or listed alias.
- With Ollama on a CPU, a plan takes one to two minutes.
- The cloud deployment requires OpenAI, since serverless functions cannot keep a local model loaded.

### 1.7 Assumptions and dependencies

- The OpenAI API, Wikivoyage, and Vercel remain available with their current interfaces and terms.
- The Next.js hosting configuration allows a server-side request to run for at least 180 seconds.
- Wikivoyage text remains licensed under CC BY-SA 4.0.

### 1.8 Definitions

| Term | Definition |
| --- | --- |
| Agent | A web service with one job: Host, Flight, Stay, or Activities |
| Host | The agent that receives a trip request and calls the other three |
| Trip plan | The Host's merged response: offers, errors, and sources |
| Offer | One generated suggestion: a flight, a stay, or an activity |
| Guidance | Wikivoyage passages added to a specialist's prompt |
| Guidance index | The vector store of embedded Wikivoyage passages |
| Embedding identity | The provider, model, and vector size that built an index |
| Partial plan | A trip plan in which at least one agent failed and at least one succeeded |

## 2. Requirements

"Shall" marks a mandatory requirement and "should" a target.

### 2.1 External interfaces

**[TP-SRS-001]** Every agent shall expose `POST /run`, `GET /healthz`, `GET /readyz`, and `GET /`.

**[TP-SRS-002]** `GET /healthz` shall return `{"status": "ok", "service": "<name>"}` and shall never require an API key.

**[TP-SRS-003]** The Host's `POST /run` shall accept a travel request and return a trip plan as JSON.

**[TP-SRS-004]** When a request body fails validation, an agent shall respond with status `422` and list the invalid fields.

**[TP-SRS-005]** Each agent shall accept an optional `X-Request-ID` header, use it in its log lines, and the Host shall forward it to the specialists.

**[TP-SRS-006]** Each agent shall serve its OpenAPI schema at `/openapi.json`.

### 2.2 Functions

#### 2.2.1 Trip form (web application)

**[TP-SRS-010]** The web application shall display a form with the fields: origin, destination, start date, end date, budget in USD, and number of travellers.

**[TP-SRS-011]** The travellers field shall accept whole numbers from 1 to 9 and default to 1.

**[TP-SRS-012]** The budget field shall accept amounts of at least 100 in steps of 50.

**[TP-SRS-013]** If the origin or destination is empty when the user submits, then the web application shall show a warning and shall not send the request.

**[TP-SRS-014]** If the end date is not after the start date when the user submits, then the web application shall show a warning and shall not send the request.

**[TP-SRS-015]** While a plan is being requested, the web application shall disable the submit button.

#### 2.2.2 Planning progress (web application)

**[TP-SRS-020]** While a plan is being requested, the web application shall display a progress indicator at the top of the results area showing the elapsed time, updated at least every second.

**[TP-SRS-021]** When the plan arrives, the web application shall mark the progress indicator as complete if no part failed, or partial if at least one part failed.

**[TP-SRS-022]** If the Host cannot be reached, returns an error status, or does not respond within 180 seconds, then the web application shall mark the progress indicator as failed and display a message saying the planning service is unavailable.

#### 2.2.3 Results display (web application)

**[TP-SRS-030]** The web application shall display flights, accommodation, and activities in three separate tables.

**[TP-SRS-031]** For each failed part listed in the plan's `errors`, the web application shall display a warning naming the part and its message.

**[TP-SRS-032]** When the plan contains sources, the web application shall display a collapsed "Sources" section listing each source's title as a link, with its license.

**[TP-SRS-033]** The web application shall state that suggestions are illustrative and not live or bookable.

#### 2.2.4 Server-side access to the Host (web application)

**[TP-SRS-040]** The web application shall send trip requests to the Host from server-side code, never directly from the browser.

**[TP-SRS-041]** The web application shall read the Host address (`HOST_SERVICE_URL`) and API key (`HOST_API_KEY`) from server-side environment variables.

**[TP-SRS-042]** The web application shall not include the Host API key in any response, page, or script sent to the browser.

**[TP-SRS-043]** When `HOST_API_KEY` is set, the web application shall send it to the Host in the `X-API-Key` header.

#### 2.2.5 Request validation (agents)

**[TP-SRS-050]** The Host shall reject a travel request unless: origin and destination are 2 to 120 characters; `end_date` is after `start_date`; `budget` is greater than 0; `travellers` is 1 to 9; `currency`, if given, is three letters; `preferences` has at most 20 items; and `user_id`, if given, is at most 128 characters.

**[TP-SRS-051]** The Host shall collapse repeated spaces in origin and destination, and convert the currency to upper case.

**[TP-SRS-052]** If `request_id` or `trip_id` is absent, then the Host shall generate a UUID for it.

**[TP-SRS-053]** If `currency` is absent, the Host shall use `USD`.

#### 2.2.6 Trip planning (Host)

**[TP-SRS-060]** The Host shall send each valid travel request to the Flight, Stay, and Activities agents concurrently.

**[TP-SRS-061]** The Host shall validate each agent's response against its response model.

**[TP-SRS-062]** The Host shall return one trip plan containing `request_id`, `trip_id`, `flights`, `stay`, `activities`, `errors`, and `sources`.

**[TP-SRS-063]** If an agent cannot be reached, returns an error status or invalid JSON, or does not respond within `DOWNSTREAM_TIMEOUT_SECONDS`, then the Host shall record an entry in `errors` for that part with the message "Service is temporarily unavailable." and still return the other parts.

**[TP-SRS-064]** The Host shall return status `200` when at least the request was valid, including when some or all agents failed.

**[TP-SRS-065]** The Host shall merge the agents' sources, drop malformed entries, and remove duplicates by URL.

**[TP-SRS-066]** The Host shall not call a language model.

#### 2.2.7 Suggestion generation (Flight, Stay, Activities)

**[TP-SRS-070]** Each specialist shall return at least one offer or an explicit `error`; an empty response without an error is invalid.

**[TP-SRS-071]** Each specialist shall request JSON constrained by its response schema from the language model, at temperature 0.

**[TP-SRS-072]** Each specialist shall validate the model's answer against its full response model before returning it.

**[TP-SRS-073]** If the model call fails, times out after `LLM_TIMEOUT_SECONDS`, is rejected, or returns output that fails validation, then the specialist shall return the error "Flight planner is temporarily unavailable." (or "Stay planner ...", "Activity planner ...") and log the underlying cause.

**[TP-SRS-074]** Every offer price shall be zero or more, with a three-letter currency.

**[TP-SRS-075]** Each specialist's prompt shall instruct the model not to present suggestions as live or bookable.

**[TP-SRS-076]** The Activities agent shall use the request's `preferences`, or "general sightseeing" when none are given.

**[TP-SRS-077]** The application shall support Ollama and OpenAI as model providers, selected by `LLM_PROVIDER`, without code changes.

#### 2.2.8 Guidance retrieval (Flight, Stay, Activities)

**[TP-SRS-080]** When retrieval is enabled and the destination is in the index, each specialist shall add up to `RAG_TOP_K` (default 2) passages to its prompt.

**[TP-SRS-081]** Each specialist shall retrieve only from its own sections: Flight from Get in and Get around; Stay from Sleep, Stay safe, and Understand; Activities from See, Do, Eat, and Drink.

**[TP-SRS-082]** Retrieval shall return only English passages for the requested destination that have not expired.

**[TP-SRS-083]** The application shall resolve destination aliases listed in the destination file, such as "NYC" for New York City.

**[TP-SRS-084]** If the destination is not in the index, then the specialist shall skip retrieval without making an embedding call.

**[TP-SRS-085]** If retrieval fails for any reason (no index, packages missing, embedding failure, or a lookup exceeding `RAG_TIMEOUT_SECONDS`), then the specialist shall plan without guidance and log the reason.

**[TP-SRS-086]** If the index's embedding identity differs from the configured one, then the application shall disable retrieval and log the mismatch.

**[TP-SRS-087]** Retrieved text shall be placed inside `<guidance>` markers with an instruction to treat it as reference only, with any copies of the markers removed from the text.

**[TP-SRS-088]** Each passage added to a prompt shall be at most 700 characters, and all guidance together at most 2,400 characters.

**[TP-SRS-089]** Each specialist shall return the sources of the passages it used, each with a title, URL, and license.

**[TP-SRS-090]** Sources shall come only from the index; the schema given to the model shall have no field for sources.

#### 2.2.9 Guidance index management

**[TP-SRS-100]** The application shall provide a command that builds the guidance index from the destinations listed in `data/rag/destinations.txt`.

**[TP-SRS-101]** The ingest command shall keep only the article sections used by some agent, split them into passages of about 300 tokens, and store each with its destination, section, title, source URL, revision ID, license, language, and validity dates.

**[TP-SRS-102]** Passages shall expire one year after they are downloaded.

**[TP-SRS-103]** Re-ingesting a destination shall replace its passages rather than duplicate them.

**[TP-SRS-104]** The ingest command shall cache downloaded articles for 30 days, with an option to download them again.

**[TP-SRS-105]** The ingest command shall accept a list of destinations to ingest instead of the whole file.

**[TP-SRS-106]** The ingest command shall build either a Chroma index (self-hosted) or a file-based index (cloud), and shall refuse to build a cloud index with non-OpenAI embeddings.

**[TP-SRS-107]** Each index shall record the embedding identity that built it.

#### 2.2.10 API protection

**[TP-SRS-110]** When `HOST_API_KEY` is set, the Host shall reject a `POST /run` request without a matching `X-API-Key` header with status `401`.

**[TP-SRS-111]** The Host shall compare API keys in constant time.

**[TP-SRS-112]** When `HOST_API_KEY` is not set, the Host shall accept requests without a key.

**[TP-SRS-113]** The specialist agents shall not be reachable from outside the deployment.

#### 2.2.11 Metrics

**[TP-SRS-120]** When `OTEL_EXPORTER_OTLP_ENDPOINT` is set, each agent shall push HTTP request metrics, model call durations by outcome, token usage by type, and retrieval durations by outcome over OTLP at least once a minute.

**[TP-SRS-121]** When `OTEL_EXPORTER_OTLP_ENDPOINT` is not set, the application shall send no metrics.

**[TP-SRS-122]** A failure to export metrics shall not affect request handling.

### 2.3 Usability requirements

**[TP-SRS-130]** Every form field in the web application shall have a visible label and be reachable and operable with the keyboard alone.

**[TP-SRS-131]** The web application shall be usable at screen widths from 360 pixels upward without horizontal scrolling.

**[TP-SRS-132]** Error and warning messages shown to users shall be plain sentences that do not expose provider names, stack traces, or keys.

**[TP-SRS-133]** The web application should display results without a full page reload.

### 2.4 Performance requirements

**[TP-SRS-140]** With OpenAI in the cloud deployment, the Host should return a trip plan within 10 seconds when its functions are warm, and within 30 seconds from a cold start.

**[TP-SRS-141]** The total time for a plan should be close to the slowest specialist's time, not the sum of all three.

**[TP-SRS-142]** Timeouts shall be nested so each caller waits longer than the call it makes: the web application waits 180 seconds for the Host, and `DOWNSTREAM_TIMEOUT_SECONDS` shall be greater than `LLM_TIMEOUT_SECONDS` and less than 180.

**[TP-SRS-143]** Each specialist shall cache retrieval results in memory, keyed by agent, destination, and day, holding up to 256 entries.

**[TP-SRS-144]** In the self-hosted setup, the language model runtime should keep the chat and embedding models loaded together for at least 30 minutes.

### 2.5 Logical database requirements

**[TP-SRS-150]** The application shall store no user data and no trip plans; nothing from a request shall outlive it except log lines and metric counts.

**[TP-SRS-151]** The guidance index shall be read-only while serving requests.

**[TP-SRS-152]** The cloud guidance index shall be stored as files committed to the repository and bundled into each deployment.

### 2.6 Design constraints

**[TP-SRS-160]** The web application shall be built with Next.js.

**[TP-SRS-161]** The agents shall be Python 3.11 FastAPI services sharing one codebase, with the agent selected by `APP_MODULE`.

**[TP-SRS-162]** All data contracts between services shall be defined once, in `shared/schemas.py`, and validated at every service boundary.

**[TP-SRS-163]** All configuration shall come from environment variables.

**[TP-SRS-164]** The application shall be deployable both self-hosted with Docker Compose, including the web application as a container, and on Vercel, including the web application.

**[TP-SRS-165]** On Vercel, only the web application and the Host shall have public routes; the specialists shall be reached through private service bindings.

**[TP-SRS-166]** All dependency versions shall be pinned.

### 2.7 Standards compliance

**[TP-SRS-170]** Every displayed source shall carry its title, URL, and license, as CC BY-SA 4.0 requires for Wikivoyage text.

**[TP-SRS-171]** The ingest command shall identify itself to the MediaWiki API with a contact URL, as Wikimedia's API policy asks.

**[TP-SRS-172]** Dates in the API shall use ISO 8601 (`YYYY-MM-DD`), and currencies ISO 4217 three-letter codes.

### 2.8 Software system attributes

**Reliability**

**[TP-SRS-180]** A failure in one agent shall never prevent the other agents' results from reaching the user.

**[TP-SRS-181]** Retrieval shall never turn an otherwise successful plan into an error.

**Security**

**[TP-SRS-182]** Secrets shall never be stored in source code, Terraform state, or version control, and shall be excluded from Docker and Vercel uploads.

**[TP-SRS-183]** Each service shall receive only the secrets it uses.

**[TP-SRS-184]** The cloud deployment shall serve all public traffic over HTTPS.

**[TP-SRS-185]** CI shall authenticate to cloud providers without stored long-lived keys.

**Maintainability and portability**

**[TP-SRS-186]** Switching the model provider or vector store shall require only configuration changes.

**[TP-SRS-187]** The automated tests shall run without any external service.

**Cost**

**[TP-SRS-188]** The self-hosted setup shall require no paid service, and the cloud deployment should cost nothing while idle beyond per-request model usage.

## 4. Supporting information

**Change from the SDD.** The SDD describes a Streamlit interface (`travel_ui.py`) running on Streamlit Community Cloud. Replacing it with Next.js changes:

- **Hosting:** the interface can run on Vercel beside the agents, instead of on a separate platform, because Next.js does not need an always-on server.
- **Secret handling:** the browser runs Next.js client code, so the Host API key must stay in server-side code (TP-SRS-040 to 043). Streamlit ran entirely on the server, so this was implicit before.
- **Routing:** on Vercel, public routes are split between the web application and the Host (TP-SRS-165), instead of all routes going to the Host.
- **Container image:** the self-hosted UI image becomes a Node.js image instead of `ui-runtime`.
- **Tests:** `tests/test_ui.py` is replaced by Next.js tests.

The agents, their API, retrieval, and data contracts are unchanged.
